= Introduction to Firewall Rules in Image Mode

Before you touch the command line, let's build the mental model. This module is reading only — no commands to run — but it sets up everything you'll do in Modules 2 and 3.

== The Scenario

You're a systems administrator at *Super-Business*. The team just moved a fleet of RHEL servers to *image mode* so every host runs the same known, versioned OS image. Your job: make sure the firewall on these hosts is configured correctly — and *stays* that way.

[quote, Manager Scott]
____
Team! Great news — I opened a firewall port on one of the new image mode servers myself. Typed the command and everything. So we're basically secure now, right? ...Right?
____

[NOTE]
====
*From: Nate (Senior Sysadmin)*

Ah, Scott. He's not *wrong* — `firewall-cmd` works on an image mode host just like it always has, and a `--permanent` rule even survives image updates, because it's written to `/etc` and bootc keeps your `/etc` and `/var` across deployments. The catch is subtler: a change made by hand lives only on *that one host* and isn't captured anywhere. Build a new server from the same image and it won't have Scott's rule; a year from now nobody knows why the port is open, because its not in the image. On image mode you usually want a host's config to come *from the image*. Let me walk you through it.

-Nate
====

== What Is a bootc Host?

RHEL image mode delivers the operating system as a versioned *bootc* image. The OS content under `/usr` comes from that image and is read-only at runtime, and you update the system by building a *new* image and switching to it — rather than patching packages in place. Your configuration in `/etc` and data in `/var` are *not* replaced: bootc preserves them across updates (it does a 3-way merge on `/etc`). So a bootc host isn't locked down end to end — the bulk of the OS is swapped wholesale on update, while your local state carries over.

firewalld still runs on an image mode host exactly as it does on a conventional RHEL host. You can query zones, add ports, reload, and make rules persistent with `--permanent` — the familiar tools all work, and persistent rules survive both reboots and image updates. What changes isn't whether the tools work or whether changes stick; it's the *paradigm* you follow to manage them.

== Ways to Apply Firewall Rules

You can apply firewall rules to a RHEL host in several ways, and all of them are legitimate — the right choice depends on what you're doing:

[cols="1,2,2",options="header"]
|===
| Approach | How | Behavior on an image mode host

| *Manual / runtime*
| `firewall-cmd` on the running host
| A plain rule is runtime-only and gone on reboot; a `--permanent` rule is written to `/etc` and persists across reboots *and* image updates. Either way the change is made per host, outside the image. Ideal for testing and one-off diagnostics.

| *Automation*
| A config-management tool such as the RHEL system roles (the `firewall` role)
| Repeatable and consistent across a fleet. Applied to a running host the rule persists (in `/etc`) just like a manual `--permanent` change — but the resulting state lives on each host rather than in the image, unless the automation runs as part of the build.

| *Build-time*
| A `RUN firewall-offline-cmd ...` directive in the Containerfile
| Declarative — the rule is part of the image, so *every* host built from it comes up with the rule, no per-host step. Versioned, repeatable, and auditable.
|===

The takeaway that drives the rest of this lab:

[IMPORTANT]
====
On an image mode host, the image is the natural source of truth for a host's configuration. You *can* set firewall rules directly on a host and they'll persist — but defining them in the image makes them declarative, versioned, and identical on every host built from it.
====
